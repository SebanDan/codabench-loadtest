==============================================================================
  ÉTAPES DE TEST — Codabench Load Testing
==============================================================================

Pré-requis :
  - AWS CLI configuré (profil codabench ou autre via AWS_PROFILE)
  - Terraform apply fait (infra/load-generators)
  - Fichier .env configuré sur les instances (fait automatiquement par user-data)
  - Credentials RabbitMQ stockés dans AWS SSM Parameter Store :
      /codabench-loadtest/rabbitmq-user       (String)
      /codabench-loadtest/rabbitmq-password    (SecureString, chiffré)
    Terraform les lit automatiquement via data sources (data.tf) et les
    injecte dans le .env du master au déploiement. Aucun secret en dur
    dans le code.
  - Services Codabench démarrés sur 10.0.11.11 (voir section TROUBLESHOOTING)

IMPORTANT — Routage réseau Paris :
  Les tests Paris utilisent l'IP directe de l'instance Codabench (10.0.11.11:80
  via Caddy) et NON l'ALB DNS. L'ALB est internet-facing (IPs publiques), donc
  le trafic depuis le subnet privé Locust ne peut pas l'atteindre (hairpin NAT).
  Seules les régions distantes (US East, Asia Pacific) passent par l'ALB via
  l'internet public — c'est voulu pour mesurer la latence réelle.


==============================================================================
  PHASE 1 — Web / API seul (baseline sans queue)
==============================================================================

But : mesurer les performances de l'API Django seule, sans déclencher
      de traitement queue/worker. Ça donne la baseline web.

1. Lancer le test smoke (GET endpoints uniquement) :

   ./scripts/run_test.sh --tags normal --users 50 --spawn-rate 5 --duration 10m \
     --run-name phase1_smoke --paris-only

2. Ouvrir l'UI Locust pour suivre en temps réel :

   aws ssm start-session \
     --target "$(terraform -chdir=infra/load-generators output -raw paris_locust_master_id)" \
     --document-name AWS-StartPortForwardingSession \
     --parameters '{"portNumber":["8089"],"localPortNumber":["8089"]}' \
     --profile codabench

   -> http://localhost:8089

3. Collecter les résultats :

   ./scripts/collect_results.sh phase1_smoke

4. Vérifier :
   - p95 response time < 2s
   - Error rate < 1%
   - Pas de 5xx


==============================================================================
  PHASE 2 — Queue / Workers seul (soumissions)
==============================================================================

But : mesurer le comportement de RabbitMQ + compute workers sous charge,
      et reproduire les 3 failure modes du client.

--- Test 2a : Soumissions normales ---

1. Démarrer le monitoring RabbitMQ (dans un terminal séparé, via SSM) :

   aws ssm start-session \
     --target "$(terraform -chdir=infra/load-generators output -raw paris_locust_master_id)" \
     --profile codabench

   # Sur l'instance :
   cd /opt/codabench-loadtest
   uv run python -m codabench_loadtest.common.rabbitmq_monitor \
     --duration 900 --interval 5 --output runs/phase2a_rabbit.csv

2. Lancer le test de soumissions normales :

   ./scripts/run_test.sh --tags normal --users 20 --spawn-rate 2 --duration 15m \
     --run-name phase2a_normal --paris-only

3. Observer :
   - Queue depth dans les logs du monitor (doit rester stable, pas exploser)
   - Consumer count (doit correspondre au nombre de workers Codabench)
   - Temps de soumission bout en bout dans l'UI Locust

4. Collecter :

   ./scripts/collect_results.sh phase2a_normal


--- Test 2b : OOM (modèles lourds) ---

1. Démarrer le monitoring RabbitMQ (même commande, output différent) :

   uv run python -m codabench_loadtest.common.rabbitmq_monitor \
     --duration 600 --interval 5 --output runs/phase2b_rabbit.csv

2. Lancer le test heavy :

   ./scripts/run_test.sh --tags heavy --users 5 --spawn-rate 1 --duration 10m \
     --run-name phase2b_heavy --paris-only

3. Observer :
   - Est-ce que les workers Codabench crashent (OOM) ?
   - Est-ce que la queue se vide quand même ou les messages restent bloqués ?
   - Memory RabbitMQ dans le CSV (node_memory_bytes)

4. Collecter :

   ./scripts/collect_results.sh phase2b_heavy


--- Test 2c : Annulation de soumissions ---

1. Démarrer le monitoring RabbitMQ :

   uv run python -m codabench_loadtest.common.rabbitmq_monitor \
     --duration 600 --interval 5 --output runs/phase2c_rabbit.csv

2. Lancer le test clumsy :

   ./scripts/run_test.sh --tags clumsy --users 10 --spawn-rate 2 --duration 10m \
     --run-name phase2c_clumsy --paris-only

3. Observer :
   - Est-ce que le worker est libéré après annulation ?
   - messages_unacked : est-ce qu'il y a des messages orphelins ?
   - Erreurs Locust : race condition, états incohérents ?

4. Collecter :

   ./scripts/collect_results.sh phase2c_clumsy


==============================================================================
  PHASE 3 — Combined (web + queue, multi-région)
==============================================================================

But : simuler les conditions réelles d'une compétition avec des utilisateurs
      du monde entier. On combine Phase 1 + Phase 2.

1. Démarrer le monitoring RabbitMQ :

   uv run python -m codabench_loadtest.common.rabbitmq_monitor \
     --duration 1800 --interval 5 --output runs/phase3_rabbit.csv

2. Lancer le test sur les 3 régions :

   ./scripts/run_test.sh --tags normal --users 100 --spawn-rate 10 --duration 30m \
     --run-name phase3_combined

   (Paris + US East + Asia Pacific, tous en parallèle)

3. Observer :
   - Latence par région dans l'UI Locust (Paris vs US vs Asia)
   - Queue depth sous 100 users simultanés
   - Est-ce que RabbitMQ tient ou sature comme lors de l'incident ?
   - Temps de traitement bout en bout

4. Collecter :

   ./scripts/collect_results.sh phase3_combined

==============================================================================
  TROUBLESHOOTING — Problèmes rencontrés et solutions
==============================================================================

--- Problème 1 : Services Codabench arrêtés ---

Symptôme : curl vers 10.0.11.11:80 ou :15672 retourne connection refused.
L'instance EC2 est running mais les containers Docker sont arrêtés.

Solution :
  aws ssm send-command \
    --profile codabench --region eu-west-1 \
    --instance-ids i-050519c74b8b3c800 \
    --document-name "AWS-RunShellScript" \
    --parameters 'commands=["cd /opt/codabench && docker compose -f docker-compose.prod.yml up -d"]'

Vérification :
  aws ssm send-command ... \
    --parameters 'commands=["docker ps --format \"table {{.Names}}\t{{.Status}}\""]'

Les services prennent ~1 minute à démarrer. Attendre que Django soit healthy
avant de lancer les tests.


--- Problème 2 : ALB inaccessible depuis Paris (hairpin NAT) ---

Symptôme : curl depuis le Locust master vers le DNS de l'ALB retourne
HTTP 000 / connection timed out.

Cause : l'ALB est internet-facing (IPs publiques uniquement). Le Locust
master est dans un subnet privé. Le trafic sort par le NAT Gateway vers
les IPs publiques de l'ALB, mais le retour ne fonctionne pas (hairpin NAT
non supporté par AWS NAT Gateway).

Solution : les tests Paris pointent directement vers 10.0.11.11:80 (Caddy)
au lieu du DNS ALB. Les templates Terraform et run_test.sh ont été mis à
jour pour utiliser la variable codabench_app_ip. Les régions distantes
(US East, Asia Pacific) continuent d'utiliser l'ALB via l'internet public.


--- Problème 3 : Security groups manquants ---

Symptôme : connexion timeout vers 10.0.11.11 sur les ports 80 ou 15672.

Cause : les règles de SG n'autorisaient pas le trafic Locust vers le SG
de l'instance Codabench.

Solution : ajout de 3 règles dans security_group.tf du module Paris :
  - Egress Locust -> Codabench SG port 80 (trafic de test)
  - Ingress Codabench SG <- Locust SG port 80 (accepter le trafic)
  - Ingress ALB SG <- Locust SG port 80 (pour les tests ALB futurs)
  (La règle RabbitMQ :15672 existait déjà)


--- Problème 4 : Code pas sur la bonne branche sur les instances ---

Symptôme : module not found, ou scénarios manquants.

Cause : le user-data clone la branche définie dans variables.tf (par défaut
main). Si le code est sur une feature branch, les instances ont l'ancienne
version.

Solution : utiliser --branch dans run_test.sh :
  ./scripts/run_test.sh --branch 27-feat-provision-locust-infra --tags normal ...

Ou merger la feature branch dans main avant de tester.
